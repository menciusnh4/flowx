## 1. 功能概述

账号分析功能的核心不是数据展示，而是 **"诊断问题 → 给出建议 → 指导行动"** 的闭环。基于 FlowX 已有的 CDP 浏览器自动化能力，直接从各平台创作者后台采集精准的账号数据，结合规则引擎和 LLM 生成可执行的优化建议。

> 💡 **核心价值**
> - **对用户**：不仅知道数据差，还知道为什么差、怎么改
> - **对产品**：从"发布工具"升级为"运营助手"，提升用户粘性和付费意愿
> - **对技术**：复用已有 CDP + 平台适配器基础设施，数据采集成本低

### 1.1 功能模块组成

| 模块 | 说明 |
|------|------|
| 📊 **数据概览** | 账号核心指标看板、趋势图、健康度评分 |
| 🎯 **作品诊断** | 单作品数据分析 + 问题定位 + 优化建议 |
| 🆚 **对标分析** | 多账号对比、竞品监控、差距分析 |
| 📈 **趋势洞察** | 粉丝增长、互动率、完播率等指标趋势 |
| 📝 **周期报告** | 周/月自动生成运营报告（后续版本） |

### 1.3 数据来源与优势

| 数据来源 | 精度 | 指标丰富度 | 实现方式 |
|---------|------|-----------|---------|
| **创作者后台数据**（核心） | 100% 精确 | 高（完播率/流量来源/画像） | CDP 登录态 + DOM 提取 |
| **公开主页数据**（对标用） | 精确但维度少 | 低（点赞/评论/收藏） | 公开页面 DOM 提取 |
| **CDP 视觉分析**（护城河） | 自主分析 | 独特（封面质量/高光时刻） | 截图 + 视觉模型 |

### 2.2 核心定位差异

| 维度 | SaaS 竞品（蝉妈妈/飞瓜） | FlowX 账号分析 |
|------|-------------------------|----------------|

| **隐私性** | 数据在第三方服务器 | 全部本地存储，不上传云端 |
| **独特优势** | 数据量大、榜单全 | 数据精准、隐私安全、与发布闭环 |

### 4.2 核心设计原则

| 原则 | 描述 |
|------|------|
| **复用优先** | 最大限度复用 AccountService 的 partition/cookie/窗口/CDP 基础设施，不重复造轮子 |
| **平台隔离** | 各平台数据采集逻辑独立到各自 Collector 文件，修改一个平台不影响其他 |
| **采集与分析分离** | 数据采集是一层，诊断分析是另一层，可独立演进和测试 |
| **渐进增强** | 规则引擎先上（快、稳、可解释），LLM 后上（个性化、自然语言） |
| **本地优先** | 所有数据本地存储，不上传云端，保障用户隐私 |
| **增量采集** | 只采集上次之后的新数据，避免全量重复抓取 |

## 5. 数据采集层

### 5.1 Collector 体系结构

采用**平台适配器 + 采集器基类**的模式，与现有发布平台适配器思路一致。

```
src/main/services/analytics/
├── AnalyticsService.ts          # 总调度服务
├── collector/
│   ├── BaseCollector.ts         # 采集器基类（窗口管理/导航/通用工具）
│   ├── DouyinCollector.ts       # 抖音数据采集器
│   ├── XiaohongshuCollector.ts  # 小红书数据采集器
│   ├── KuaishouCollector.ts     # 快手数据采集器
│   └── BenchmarkCollector.ts    # 公开页对标数据采集器
├── diagnosis/                   # 诊断引擎（见 §6）
├── benchmark/                   # 对标分析（见 §7）

    └── AnalyticsStore.ts
```

### 5.2 BaseCollector 基类

```typescript
/**
 * 数据采集器基类
 * 封装窗口创建、cookie 注入、导航等待等通用逻辑
 * 复用 AccountService 的基础设施
 */
abstract class BaseCollector {
  protected platform: PlatformType;
  protected accountId: string;

  /**
   * 创建/复用采集窗口（隐藏模式，复用 partition）

### 5.4 采集策略

| 策略 | 说明 |
|------|------|
| **手动触发** | 用户点击"刷新数据"按钮，立即开始采集 |
| **定时采集** | 可配置频率（每 2/4/8/24 小时），后台自动采集 |
| **增量采集** | 记录上次采集时间和最后一条作品 ID，只采集新发布的作品 |
| **深度采集** | 对高关注的作品（如爆款/诊断为问题的作品）定期刷新详细数据 |
| **队列控制** | 同时最多 N 个采集任务并行（默认 2，避免开太多窗口占资源） |
| **失败重试** | 采集失败自动重试最多 3 次，指数退避 |

### 5.5 采集窗口复用策略

为避免频繁创建销毁 BrowserWindow，采用**窗口池**策略：

1. 每个账号最多复用 1 个采集窗口
2. 采集完成后窗口保持 5 分钟，期间有新任务直接复用
3. 5 分钟空闲后自动关闭窗口，释放资源
4. 窗口复用前检查登录态，过期则重新注入 cookie

## 6. 诊断引擎

### 6.1 诊断流程

```
作品原始数据
    ↓
指标计算（互动率/转粉率/点击率等）
    ↓
行业基准对比（按平台+粉丝量级+内容类型）
    ↓
规则匹配（多维度规则库）
    ↓
问题识别（按严重程度排序）
    ↓
建议生成（从建议模板库匹配）
    ↓
综合评分（各维度加权）
    ↓
诊断结果（WorkDiagnosis）
```

### 6.2 诊断维度与规则

#### 6.2.1 钩子质量（Hook）

| 规则 | 触发条件 | 严重程度 | 建议 |
|------|---------|---------|------|
| 完播率偏低 | 完播率 < 行业基准 warning | high/medium | 将最精彩的画面/金句前置到前3秒 |
| 前5秒流失高 | 5秒完播率 < 50% | high | 优化开头，增加悬念或视觉冲击 |
| 平均时长短 | 平均播放时长 < 视频时长 30% | high | 精简内容，加快节奏 |

#### 6.2.2 内容质量（Content）

| 规则 | 触发条件 | 严重程度 | 建议 |
|------|---------|---------|------|
| 完播率一般 | 完播率 在 warning ~ good 之间 | low | 优化内容结构，增加信息密度 |
| 进度条中段流失 | 留存曲线在 30%-70% 区间下降快 | medium | 中段增加转折或干货，避免拖沓 |

#### 6.2.3 互动转化（Engagement）

| 规则 | 触发条件 | 严重程度 | 建议 |
|------|---------|---------|------|
| 互动率偏低 | 互动率 < 行业基准 warning | medium | 增加互动引导，如提问、投票、求赞 |
| 评论率偏低 | 评论/播放 < 0.1% | low | 在内容中设置争议点或讨论话题 |
| 收藏率偏低 | 收藏/播放 < 0.5%（教程类） | medium | 增加实用价值，整理清单/工具/方法 |

#### 6.2.4 转粉效率（Conversion）

| 规则 | 触发条件 | 严重程度 | 建议 |
|------|---------|---------|------|
| 转粉率偏低 | 转粉率 < 行业基准 warning | medium | 结尾增加关注引导，明确关注价值 |
| 高播放低涨粉 | 播放量 Top 10 但涨粉量不在 Top 10 | high | 检查内容是否偏离账号定位，强化人设 |

#### 6.2.5 封面/标题点击率（ClickThrough）

| 规则 | 触发条件 | 严重程度 | 建议 |
|------|---------|---------|------|
| 点击率偏低 | 点击率 < 行业基准 warning | high | 优化封面设计和标题文案，提升点击欲望 |
| 曝光高播放低 | 曝光量高但播放量低 | high | AB 测试不同封面/标题组合 |

### 6.3 综合评分算法

```typescript
function calculateOverallScore(dimensionScores): number {
  const weights = {
    hook: 0.25,          // 钩子（决定是否看下去）
    content: 0.25,       // 内容质量（决定是否看完）
    engagement: 0.2,     // 互动（决定是否推荐）
    conversion: 0.15,    // 转粉（决定账号价值）
    clickThrough: 0.15,  // 点击率（决定流量上限）
  };

  let total = 0;
  for (const [dim, weight] of Object.entries(weights)) {
    total += (dimensionScores[dim] ?? 60) * weight;
  }
  return Math.round(total);
}
```

## 7. 对标分析模块

### 7.1 两种对标模式

| 模式 | 数据来源 | 数据粒度 | 实现难度 | 优先级 |
|------|---------|---------|---------|--------|
| **模式 A：自有账号互标** | FlowX 中已授权的同平台多个账号 | 完整后台数据（完播率/画像/流量来源） | 低（复用采集逻辑） | **P0** |
| **模式 B：公开主页对标** | 竞品账号的公开主页 | 仅公开数据（点赞/评论/收藏/粉丝） | 中（需处理公开页结构） | P1 |

### 7.2 模式 A：自有账号互标

**使用场景**：用户在 FlowX 中授权了同一个平台的多个账号（如两个抖音号），可以直接选择其中一个或多个作为对标账号。

**优势**：
- 数据完整度 100%（所有后台指标都有）
- 采集成本为零（复用已有采集逻辑）
- 对比维度丰富，价值高

**对比维度**：

| 对比维度 | 说明 |
|---------|------|
| 粉丝量级对比 | 总粉丝数、增长速度、增长趋势 |
| 互动率对比 | 平均互动率、互动率趋势 |
| 完播率对比 | 平均完播率、完播率分布 |
| 发布频率对比 | 周/月发布数量、发布时间分布 |
| 爆款率对比 | 爆款（播放/点赞 Top 10%）占比 |
| 内容类型分布 | 不同内容类型的数量与表现 |
| 最佳发布时间 | 高互动作品的发布时段分析 |

### 7.3 模式 B：公开主页对标

**使用场景**：用户输入竞品账号的主页 URL 或 ID，系统采集其公开数据进行对比。

**技术实现**：
- 打开对标账号的公开主页
- 解析粉丝数、作品数、获赞数等公开数据
- 滚动加载最近 N 条作品的公开指标（点赞/评论/收藏）
- 保存为 BenchmarkSnapshot

**公开页采集挑战与对策**：

| 挑战 | 解决方案 |
|------|---------|
| 登录墙（未登录看不到数据） | 使用已登录账号的 partition 访问（复用 FlowX 中任一同平台账号的登录态） |
| 反爬/限流 | 降低采集频率、随机延时、模拟真人滚动 |
| 数据不完整（无非公开指标） | 在 UI 上明确标注"公开数据"，与自有账号数据区分 |
| 页面结构变化快 | 选择器定期维护，增加多套 fallback 选择器 |

### 13.2 作品列表采集链路（推荐使用 CDP API 监听方式）

              │
              ▼

              │
              ▼

              │

              │

### 13.3 监听的真实接口

**URL**：`GET https://www.zhihu.com/api/v4/creators/creations/v2/all`

**Query 参数**（与页面完全一致，因此直接监听浏览器请求即可，无需自行构造）：
```
start=0&end=0&limit=10&offset=0&need_co_creation=1&sort_type=created
```

**响应结构**（顶层无 `success` / `code` 字段）：
```ts

    type: 'answer' | 'article' | 'pin' | 'zvideo' | 'video' | 'question' | string;

### 13.5 翻页与停止策略（解决「4 条作品抓 5 页 20 条重复」等问题）

| 触发条件 | 行为 |
|---|---|
| `paging.is_end === true` | **立即 break**，不再点下一页，不管 limit 是否达标 |
| `paging.totals` 已拿到（如 `5`） | 日志打印 `totals API 返回作品总数: N`，不截断，但可用于事后对账 |
| 同 `workId` 已在 `seenIds` 中 | `continue` 跳过（跨页/重复触发 API 的去重基础） |
| `incremental.lastWorkId === workId` | 标记 `hitIncrementalStop=true`，**连当前页的后续 item 都不处理** |
| `incremental.lastWorkPublishTime >= publishTime` | 同上（只采集更新于上次采集时间点的新作品） |
| 点下一页按钮返回 `false`（没找到或 disabled） | `break`，停止翻页 |
| 下一页 `waitForNewResponse(15000)` 超时 | `break`，记录 warn |
| 单页解析 `added === 0` 且未增量停止 | `break`（翻页失败但又没命中 API 异常的兜底） |
| `page >= 50` | 保险上限 break，防止死循环 |
| CDP Debugger 附加 / 响应解析异常 | 整条链路 `catch` → `stopNetworkCollect()` → **回退 DOM 解析方式**，保持可用性 |

### 13.6 回退 DOM 解析方式（Fallback）

当 CDP 监听方式在 try 块里任何一步失败（窗口未初始化、Debugger 附加失败、第一页未拿到响应等），会自动走 `collectWorksFallback`：

- 页面：仍然是 `https://www.zhihu.com/creator/manage/creation/all`
- 解析逻辑：`extractWorksPage()` → 遍历包含「编辑 + 数据 + 查看评论」三个操作的作品行，按行内文本解析
- 指标提取特殊规则（真实页面格式已确认）：
  - 标签行支持「数值在前（i-1 或 i-2 双向前看）」—— 解决作品（想法 + 图片）行 `[2, 114, 被浏览, ...]` 第 1 个 2 是图片数、真正 views=114 被误判成 2 的问题
  - `收藏 → favorites`；`喜欢 → likesZhihu`（已解耦，不再互相覆盖）
  - `MM-DD` 发布时间自动补当年年份，若解析出日期晚于今天则回退去年
  - 标题自动去除开头「回答/文章/视频/想法/提问/专栏/播客」类型前缀

## 11. 技术坑点与解决方案

### 11.1 平台数据页面结构不稳定

**问题**：创作者后台的数据中心页面可能随平台版本更新而改变 DOM 结构，导致选择器失效。

**解决方案**：
1. **多层 fallback 选择器**：每个数据字段准备 2-3 套选择器（按优先级排序），第一套失效自动尝试下一套
2. **模糊匹配 + 关键词定位**：不依赖精确 class 名，而是通过"找到含'完播率'文字的元素 → 找相邻的数值元素"这种方式定位
3. **采集结果校验**：采集后校验数据合理性（如数值是否为正数、是否在合理范围），异常时告警
4. **选择器配置化**：平台选择器抽成独立配置文件，更新选择器不需要改核心逻辑

### 11.2 数据加载慢（SPA + 异步接口）

**问题**：创作者数据中心通常是 SPA，数据通过接口异步加载，DOM 渲染有延迟。

**解决方案**：
1. **等待策略**：导航后等待特定 DOM 元素出现（而不是固定 sleep），超时则重试
2. **轮询检测**：用 `setInterval` 轮询目标元素是否出现，出现后再执行提取
3. **监听网络请求**：通过 CDP 监听 `Network.responseReceived`，直接拦截数据接口响应（更高效、更稳定）
4. **兜底：固定等待 + 重试**：以上都失败时，固定等待 3-5 秒后尝试提取

### 11.3 登录态过期

**问题**：采集时账号登录态可能已过期，导致跳转到登录页。

**解决方案**：
1. **采集前检测**：先打开一个简单页面（如首页），检测登录态
2. **过期自动刷新**：检测到过期时，自动走 AccountService 的刷新流程
3. **失败明确告知**：采集失败后明确告诉用户"登录态已过期，请先刷新账号"，并提供快速刷新按钮

### 11.4 频繁采集触发风控

**问题**：过于频繁地打开数据中心页面，可能被平台判定为异常行为。

**解决方案**：
1. **采集频率限制**：最小采集间隔 2 小时（可配置，但不允许低于 30 分钟）
2. **随机延迟**：每次操作间加入随机延迟（500-2000ms），模拟真人操作节奏
3. **窗口复用**：尽量复用已有窗口，减少"打开-关闭"的频次
4. **用户可控**：所有采集都是用户主动触发或授权的自动采集，不在后台偷跑

### 11.5 浏览器窗口资源占用

**问题**：采集需要打开浏览器窗口，太多并行采集会占用大量内存和 CPU。

**解决方案**：
1. **队列控制**：同时最多 2 个采集任务（可配置，默认 2）
2. **窗口池**：采集完成后窗口保持 5 分钟，空闲后自动关闭
3. **隐藏窗口**：采集窗口默认 `show: false`，后台运行
4. **增量采集**：只采集新数据，不全量重复抓取

### 11.6 Electron WebContentsView 遮挡问题

**问题**：对标分析页如果内嵌浏览器视图，会有 z-index 遮挡问题（与规则编辑器同样的问题）。

**解决方案**：
1. **对标数据不实时展示网页**：采集在后台隐藏窗口进行，前端只展示采集后的数据
2. **对标账号主页查看**：用户点击"查看主页"时，在浏览器页（Browser.vue）打开新标签页
3. **避免 WebContentsView + 弹窗组合**：所有分析界面都是纯前端渲染，不叠加在浏览器视图上
